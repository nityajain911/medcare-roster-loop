How it works

What is real code, what is simulated, and what is an assumption.

Real code

Check-digit rule, duplicate check, required fields, effective-date window, routing policy, the diff by clinician and site, reconciliation, partial apply and resend, and every dashboard metric.

Simulated Simulated

AI column mapping (a fuzzy matching stand-in), the provider registry (a synthetic test list, not NPPES), the provider database, claims and prior auth feed and directory and their acknowledgements, and the directory's specialty code table (an illustrative subset of NUCC taxonomy codes).

Identifiers

The prototype uses fictional, NPI-shaped identifiers with a valid check digit. They start with 9, so they are not real NPIs, and the prototype does not perform live NPPES verification.

Changes are matched by NPI plus practice plus site, because one clinician can work at several sites. Production would use stable internal ids.

Assumptions

15 minutes saved per change and 3 per confirmation, from the deck's base case. The 60-day back-date window is a plan setting.

Channels

The prototype shows one processing loop through a portal and a roster file. Other channels (CAQH, Availity, SFTP, email) would feed the same loop and are future integrations.

Not in scope

Credentialing, contracting and licensing decisions. MedCare updates the provider record that claims and prior auth systems read; it does not process claims or make prior auth decisions. Care coordination platforms would be another destination later. No patient or member data. Demo state is kept in memory per visitor and is lost when the server restarts.

Data

All names, NPIs, practices, sites and {{ plan_name }} are fictional.
