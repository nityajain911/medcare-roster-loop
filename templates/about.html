How it works

What is real code, what is simulated, and what is an assumption.

Real code

Check-digit rule, duplicate check, required fields, effective-date window, routing policy, the diff by clinician and site, reconciliation, partial apply and resend, practice corrections, roles, and every dashboard metric.

Simulated Simulated

AI column mapping (a fuzzy matching stand-in), AI email reading (keyword rules), the provider registry and its specialty codes (a synthetic test list, not NPPES), the provider database and directory and their acknowledgements, and the directory's specialty code table (an illustrative subset of NUCC taxonomy codes).

Destinations

The pilot has one destination: the plan's provider database, which feeds the directory. A change is Applied when both acknowledge it.

Claims and prior auth feeds come later. They are shown greyed out for illustration and never decide whether a change is Applied.

Identifiers

The prototype uses fictional, NPI-shaped identifiers with a valid check digit. They start with 9, so they are not real NPIs, and the prototype does not perform live NPPES verification.

Changes are matched by NPI plus practice plus site, because one clinician can work at several sites. Production would use stable internal ids.

Channels

Live in the prototype: the portal (confirm no changes), a roster file, and email, read by simulated AI. SFTP, CAQH and Availity are future channels that would feed the same loop.

The practice side is a thin portal inside the plan's provider portal, reached by single sign-on.

Roles

Practice admin sends and corrects changes. Plan analyst (approver) decides changes, runs the directory sync, fixes and reverses. A practice admin sees the plan queue read-only.

Assumptions

15 minutes saved per change and 3 per confirmation, from the deck's base case. The 60-day back-date window is a plan setting. The 2-business-day directory target is a commercial rule.

Not in scope

Credentialing, contracting and licensing decisions, claims processing and prior auth decisions. No patient or member data. Demo state is kept in memory per visitor and is lost when the server restarts.

Data

All names, NPIs, practices, sites and {{ plan_name }} are fictional.
